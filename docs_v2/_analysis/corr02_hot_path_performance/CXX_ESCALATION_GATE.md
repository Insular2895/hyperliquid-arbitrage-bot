# C++ Escalation Gate

DOCUMENTATION STATUS: FUTURE EVIDENCE GATE — C++ NOT BASELINE

A C++ challenger may be proposed only if all conditions are documented:

1. a stable hotspot is attributed with representative profiles;
2. the hotspot materially affects end-to-end tails or work/capture economics;
3. Rust rungs R1–R10 applicable to it were tested or rejected with reasons;
4. the component is pure/bounded with immutable explicit input and output;
5. it owns no critical mutable/economic truth;
6. expected gain exceeds measured FFI/marshalling/copy overhead in context;
7. a safe C ABI, ownership, unwind and threading contract is reviewable;
8. the Rust implementation remains an executable oracle/champion;
9. golden/property/fuzz/sanitizer/ABI/Replay/Shadow evidence can be run;
10. build, supply-chain, portability, crash and client-deployment costs are acceptable;
11. failure has explicit containment/fallback and cannot bypass Risk;
12. human design and implementation approval is explicit for the scoped candidate.

No universal numeric materiality threshold is chosen. A function taking only a few microseconds is not a sensible rewrite if boundary overhead approaches the saved time; measure the entire caller path.

Potentially reviewable only after proof: pure bounded parsing, decompression, checksum, serialization or numeric kernels. NetConvert is high-risk and not a first candidate. BBO C2 correctness is also too safety-sensitive to justify a first foreign-language boundary.

Risk, Inventory, Reservations, Execution state/order/fills, Recovery, Reconciliation, Accounting, nonce, signer and capability permission are RED exclusions.
